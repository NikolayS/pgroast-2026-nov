## The proposal, restated

**Problem.** The author sees many places where a spinlock guards a single load or store of a shared field, and calls this unnecessary locking. The thread names no workload or user who suffers from it. The author did not measure contention and expects the v2 checkpointer change to have no performance effect.

**Proposed design.** v1 added slock_read_*/slock_write_* helpers in spin.h, first using barriers and then pg_atomic membarrier calls for 32- and 64-bit fields, and replaced lock-protected accesses in 20 files. After objections, v2 narrows the change to checkpointer.c. It removes ckpt_lck and packs ckpt_flags with a version number into one pg_atomic_uint32, using memory barriers and race detection for the counters.

**User-visible surface.**
- v1: new C helpers slock_read_<type> and slock_write_<type> in storage/spin.h, generated by SLOCK_DEFINE_SCALAR_ACCESSORS.
- v2: CheckpointerShmem loses ckpt_lck; src/include/access/xlog.h changes, with no detail on what.
- v2: RequestCheckpoint can report a different error message when a checkpoint that started before the request fails.

**What the author claims.**
- About 105 places in 26 files take a spinlock only around one access.
- A read of CurrBytePos without insertpos_lck sees either the value before or after the update, so it is safe.
- RequestCheckpoint with CHECKPOINT_WAIT already reports failures of unrelated checkpoints, which makes the lock-free design simpler.
- The author expects no performance impact from v2 but thinks it is still useful.

**Thread state.** Andres Freund called the v1 mechanical replacement dangerous and the write-side changes wrong, and asked for one conversion at a time with analysis documented in code; Merlin Moncure showed a broken xlog.c case. v2 for the checkpointer has no replies yet.

## 3. Objections a reviewer is likely to raise

### 1. No measured contention or user problem justifies lock-free conversion

fixable · level 1b, rubric item 4 · demand, maintenance burden ("who maintains this in 10 years"), doesn't fit what Postgres is about (extension / external tool / already solved) · `demand-1`

A committer pushes the lock-free checkpointer protocol to gain nothing measurable. Later, a memory-ordering bug on ARM or POWER makes RequestCheckpoint with CHECKPOINT_WAIT return early or report the wrong failure. Users find out from an unexplained checkpoint error or a backup that did not wait.

The thread names no workload, user report or benchmark where these spinlocks cost anything. In message #10 the author says contention was not measured, and in message #13 expects v2 to have no performance effect. The checkpointer locks are taken a few times per checkpoint, which is a cold path. Every user carries the risk of subtle ordering bugs, as message #8 warns, while nobody is shown to gain. [P1] pulled a similar atomics change for the same mix of hard barrier rules and reduced need.
